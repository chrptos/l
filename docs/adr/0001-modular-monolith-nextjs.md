# ADR-0001: Next.js によるモジュラーモノリス

- ステータス: 提案
- 日付: 2026-11-17

## 背景

開発者は1〜3名、初期の利用者は数千人規模。運用の手間を最小にしつつ、成長したときに分割できる余地を残したい。MVP は Next.js（App Router）で作られている。

## 選択肢

| 案 | 長所 | 短所 |
| --- | --- | --- |
| **A. Next.js 1アプリ（モジュラーモノリス）** | デプロイ・型・トランザクションが1か所。MVP の資産を流用できる。SSR で SEO に強い | 長時間のジョブはサーバーレスの制限を受ける |
| B. フロント（Next.js）+ API サーバー（NestJS/Go 等）に分離 | 責務が明確。モバイル向け API を作りやすい | 2つのデプロイ・型の二重定義。少人数では負担が大きい |
| C. マイクロサービス | 個別にスケールできる | この規模では明らかに過剰 |

## 決定

**A** を採用する。ただし、業務ロジックを `src/modules/<domain>` に分け、画面（`app/`）はそれを呼ぶだけにする。モジュール間の依存は一方向に保つ。

## 結果

- 良い点: 1つのリポジトリ・1つのデプロイで済む。決済の Webhook と受講登録を1トランザクションで扱える。
- 悪い点: Vercel の関数の実行時間制限があるため、一斉メール配信などの重い処理は将来ジョブ基盤（Inngest 等）に切り出す必要がある。
- 見直す条件: モバイルアプリの開発、開発者が10名を超える、特定の処理だけ負荷が突出する、のいずれか。
