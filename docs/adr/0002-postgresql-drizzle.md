# ADR-0002: PostgreSQL（Neon）+ Drizzle ORM

- ステータス: 提案
- 日付: 2026-11-17

## 背景

MVP は SQLite（`node:sqlite`）を使っている。本番では注文・台帳など、整合性が重要な会計データを扱う。Vercel のようなサーバーレス環境では、ローカルファイルの SQLite は使えない。

## 選択肢

| 案 | 長所 | 短所 |
| --- | --- | --- |
| **A. PostgreSQL（Neon）** | トランザクション・制約が強い。`pg_trgm` で日本語の部分一致検索。PR ごとにブランチ DB を作れる | サーバーレスからの接続にはドライバーの選択が必要 |
| B. PostgreSQL（Supabase） | 認証・ストレージもまとめて提供 | 使わない機能が多く、Auth を自前で持つ方針と重なる |
| C. MySQL（PlanetScale 等） | スケール実績 | 日本語の部分一致検索や制約まわりで Postgres に劣る |
| D. SQLite 系（Turso） | MVP からの移行が楽 | 会計データでの実績と、周辺ツールが少ない |

ORM:

| 案 | 長所 | 短所 |
| --- | --- | --- |
| **Drizzle** | SQL に近く、生成されるクエリを予測しやすい。軽量でサーバーレスに向く | Prisma より歴史が浅い |
| Prisma | 実績・ドキュメントが豊富 | クエリエンジンが重く、複雑な集計は生 SQL になりがち |

## 決定

**PostgreSQL（Neon）+ Drizzle** を採用する。マイグレーションは `drizzle-kit` で生成し、レビューしてからコミットする。

## 結果

- 会計テーブルには CHECK 制約・外部キー・一意制約を積極的に使い、アプリのバグがあっても不正なデータが入らないようにする。
- 本番はポイントインタイムリカバリを有効にする。
- プロバイダーに依存する機能は使わない（標準の Postgres として扱う）ため、RDS などへの移行も可能。
